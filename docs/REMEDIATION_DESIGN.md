# Nirman Inventory OS — Audit Remediation Design Document

> **Generated by a 12-agent, 3-round adversarial brainstorming session.**
> Round 1: 4 agents proposed solutions from their perspectives.
> Round 2: 4 agents critiqued each other and converged on consensus.
> Round 3: 4 adversarial agents (Devil's Advocate, Edge Case Hunter, Implementation Realist, Business Owner) attacked the consensus and found 8 blockers, 12 handle-items, and a backwards priority order.
>
> **This document is the FINAL output incorporating all 3 rounds.**

---

## Executive Summary

The audit found ~90 discrepancies between `docs/PLATFORM.md` and the codebase. Through 3 rounds of adversarial debate, the remediation plan was reshaped from a "doc-first" approach into a **"fix-the-money-first"** approach, with 8 blockers identified and resolved in the design before any implementation begins.

### What Changed in Round 3

The Round 2 consensus had the right diagnosis but the **wrong priority order** and **under-specified fixes**:

1. **Priority inversion (Business Owner challenge):** Round 2 put doc fixes (Phase 1) ahead of financial bug fixes (Phase 2). The Business Owner pointed out: "My balance sheet is broken RIGHT NOW. Why is fixing the DOCUMENT higher priority than fixing my BALANCE SHEET?" → **Reordered: financial correctness first.**

2. **8 implementation blockers found:** The Round 2 proposed code would have crashed at runtime (missing `unit.project` include), double-posted GL entries (status reversal path), violated revenue recognition (scrap generation crediting revenue), and posted to accounts with no data source (ESI field doesn't exist). → **All 8 blockers resolved in this document.**

3. **Hidden complexity exposed:** The "25-line WIP fix" requires a schema migration (idempotency field), test infrastructure that doesn't exist, and a backfill script that must source from `AssetSale.costBasis` not `productionCost`. The "2-day payroll fix" requires a schema migration for ESI and splitting the `pf` field. → **Phase 2 re-estimated at 3 weeks.**

4. **Scope cuts:** 4 of 5 drift-prevention scripts cut (keep only `audit-counts.mjs`). Virtualization deferred until data volumes validated. LandParcel fields dropped. → **Total reduced from 23 to ~18 days.**

## Phase 1: Financial Correctness (~8 days)

> **Business Owner's mandate:** "Fix my money first, then fix your docs."

### 1A. WIP Capitalization — CRITICAL (4 days, not 3)

**The bug:** `postAssetSale()` credits `UNIT_ASSET` (1800) on every unit sale but NOTHING ever debits it. WIP (1500) accumulates forever. Balance sheet shows negative finished goods.

**Round 3 found 3 BLOCKERS in the Round 2 design. All resolved below:**

#### BLOCKER 1: Wiring code crashes — `unit.project` is undefined

**Problem:** `updateUnitStatus()` (`built-unit.ts:182`) loads the unit with `prisma.builtUnit.findUnique({ where: { id: unitId } })` — no `include: { project: true }`. The Round 2 wiring referenced `unit.project.companyId` → runtime crash.

**Fix:** Add `include: { project: { select: { companyId: true } } }` to the `findUnique`:
```typescript
const unit = await prisma.builtUnit.findUnique({
  where: { id: unitId },
  include: { project: { select: { companyId: true } } },
});
```

#### BLOCKER 2: Double capitalization on status reversal

**Problem:** `built-unit.ts:188-193` allows `AVAILABLE → UNDER_CONSTRUCTION → AVAILABLE`. The Round 2 guard fires on BOTH completions → 1800 debited twice.

**Fix:** Add a `capitalizedAmount Decimal @default(0)` field to `BuiltUnit` (schema migration). Check it before capitalizing:
```typescript
if (unit.status === "UNDER_CONSTRUCTION" && status === "AVAILABLE") {
  // Reallocate costs FIRST so productionCost is fresh
  await reallocateProjectCosts(tx, unit.projectId);

  const freshUnit = await tx.builtUnit.findUnique({ where: { id: unitId } });
  const productionCost = new Decimal(freshUnit.productionCost ?? 0);
  const alreadyCapitalized = new Decimal(freshUnit.capitalizedAmount ?? 0);
  const delta = productionCost.minus(alreadyCapitalized);

  if (delta.gt(0)) {
    await postWipCapitalization(tx, {
      companyId: unit.project.companyId,
      builtUnitId: unitId,
      projectId: unit.projectId,
      costBasis: delta,
      postedById: userId,
    });
    await tx.builtUnit.update({
      where: { id: unitId },
      data: { capitalizedAmount: productionCost },
    });
  }
}
```

This also **eliminates the Phase 2/Phase 3 gap** (BLOCKER 3): by calling `reallocateProjectCosts()` inside `updateUnitStatus()` and using delta-based capitalization, post-completion cost changes are handled automatically. **Delta-capitalization (formerly Phase 3) is now part of Phase 1.**

#### BLOCKER 3 (resolved by BLOCKER 2 fix): Zero productionCost gap

**Problem:** Units completing before costs are allocated get `productionCost = 0`, skip capitalization, and are never capitalized when costs arrive later.

**Fix:** Calling `reallocateProjectCosts(tx, unit.projectId)` INSIDE `updateUnitStatus()` before reading `productionCost` ensures costs are always fresh. The delta-based approach with `capitalizedAmount` handles subsequent cost changes on already-AVAILABLE units.

**However:** `reallocateProjectCosts()` THROWS when a project has costs but zero sellable area (all units PLANNED/SOLD). **Edge Case Hunter found this (EC-1.5).** Fix: add a guard in `reallocateProjectCosts()` to skip silently instead of throwing when `totalArea = 0` and the unit being capitalized has no area. Or: only call `reallocateProjectCosts()` if the project has at least one unit with area > 0.

#### Backfill Script (1 day, separate from code fix)

**Devil's Advocate found:** Backfill for SOLD units must use `AssetSale.costBasis`, NOT current `productionCost` (which may have drifted). Also must handle cancelled sales and filter to `assetType === BUILT_UNIT` only (land is already balanced).

**Backfill logic:**
1. Find all `BuiltUnit` records with status in `["AVAILABLE", "RESERVED", "SOLD", "HOLD"]` that have no `WIP_CAPITALIZATION` journal entry.
2. For SOLD units: use `AssetSale.costBasis` (the cost at sale time).
3. For AVAILABLE/RESERVED/HOLD units: use current `productionCost` (after running `reallocateProjectCosts()`).
4. Skip units with `productionCost = 0` and no sale (nothing to capitalize).
5. Post the capitalization entry dated as of the status change `updatedAt` (from AuditLog).
6. Update `capitalizedAmount` on each unit.
7. **Filter:** `assetType === BUILT_UNIT` only. Land is already balanced (`postLandPurchase` debits 1700).

#### Test Infrastructure (1 day — Implementation Realist found this is missing)

**Problem:** All existing tests (`packages/services/src/*.test.ts`) test pure helpers only. No Prisma mock, no test DB, no transaction-mocking infrastructure. Can't unit-test GL postings.

**Fix:** Build a minimal transaction-test harness. Two options:
- **Option A (recommended):** Integration test against a real Postgres test DB. Create a `vitest` config with a test database that's reset between tests. This is the most reliable approach for testing real Prisma transactions.
- **Option B:** Mock `prisma.$transaction` with `vi.mock`. Faster but less reliable — won't catch real DB constraint issues.

**Tests to write:**
1. `updateUnitStatus(unit, "AVAILABLE")` → produces Dr 1800 / Cr 1500 journal entry
2. Status reversal `AVAILABLE → UNDER_CONSTRUCTION → AVAILABLE` → does NOT double-capitalize (idempotency via `capitalizedAmount`)
3. Zero `productionCost` → calls `reallocateProjectCosts()` first, then capitalizes the real amount
4. `postWipCapitalization` with zero amount → returns null (no entry posted)

#### Schema Migration Required

```prisma
// Add to BuiltUnit model
capitalizedAmount Decimal @default(0) @db.Decimal(14, 2) // tracks total WIP capitalized to this unit
```

Run `pnpm db:generate` + `pnpm db:push` after adding the field.

#### Frontend Enhancement (2 hours)

Add abnormal-balance warning to `GeneralLedgerView` — flag asset accounts with credit balances (or liability accounts with debit balances) with a warning badge. This would have made the WIP bug immediately visible.

#### Implementation Order (within 1A)
1. Schema migration (`capitalizedAmount` field) → `pnpm db:generate` + `pnpm db:push`
2. Build test infrastructure (integration test harness)
3. Add `postWipCapitalization()` to `gl-posting.ts`

5. Fix `reallocateProjectCosts()` — guard against zero-area throw

### 1B. Scrap GL Posting (1 day)

**The bug:** `createScrapGeneration()` records stock but no GL entry. Double-entry invariant broken.

**Round 3 found 2 BLOCKERS. Both resolved below:**

#### BLOCKER 4: DPR auto-scrap bypasses `createScrapGeneration()`

**Problem:** `runDprVarianceAnalysis()` in `standard-consumption.ts:367-456` creates `ScrapGeneration` + stock movements DIRECTLY — it does NOT call `createScrapGeneration()`. GL posting wired into `createScrapGeneration()` won't fire for auto-scrap.

**Fix:** Refactor `runDprVarianceAnalysis()` to call `createScrapGeneration()` instead of creating the records inline. This ensures the GL posting fires for both manual and auto-scrap paths. If refactoring is too risky, alternatively wire `postScrapGeneration()` into `runDprVarianceAnalysis()` directly after the scrap record is created.

#### BLOCKER 5: Standalone scrap credits REVENUE at generation — violates revenue recognition

**Problem:** Round 2 design credits `ACCT.COST_RECOVERY` (4100, typed REVENUE) for standalone scrap at generation time. This recognizes revenue BEFORE the scrap is sold. Devil's Advocate and Edge Case Hunter both flagged this.

**Fix:** For standalone scrap (no project), credit `ACCT.OPERATING_EXPENSE` (6000) instead of `COST_RECOVERY`. This treats the scrap value as a reduction of operating expenses (contra-expense behavior), not as revenue. Revenue is recognized at SALE time via `postMaterialSale()` which already credits `COST_RECOVERY`.

**Revised `postScrapGeneration()`:**
```typescript
export async function postScrapGeneration(
  tx: Prisma.TransactionClient,
  opts: {
    companyId: string;
    scrapGenerationId: string;
    projectId?: string;
    totalValue: Decimal;
    postedById?: string;
  }
) {
  const value = new Decimal(opts.totalValue);
  if (value.isZero()) return null;

  // Project-linked: recover cost from WIP (correct — reduces project cost)
  // Standalone: credit OPERATING_EXPENSE (contra-expense, NOT revenue)
  // Revenue is recognized at SALE time via postMaterialSale()
  const creditAccount = opts.projectId ? ACCT.WIP : ACCT.OPERATING_EXPENSE;

  return postJournalEntry(tx, {
    companyId: opts.companyId,
    sourceType: "SCRAP_GENERATION",
    sourceId: opts.scrapGenerationId,
    memo: opts.projectId
      ? "Scrap generated — cost recovered from WIP"
      : "Scrap material generated — cost recovery",
    postedById: opts.postedById,
    lines: [
      { accountCode: ACCT.INVENTORY, debit: value, credit: 0, entityType: "ScrapGeneration", entityId: opts.scrapGenerationId },
      { accountCode: creditAccount, debit: 0, credit: value, entityType: opts.projectId ? "Project" : "ScrapGeneration", entityId: opts.projectId ?? opts.scrapGenerationId },
    ],
  });
}
```

**Follow-up:** Adjust `projectTotalCost()` in `valuation.ts` to avoid double-counting — once WIP is reduced at generation time, the costing layer should not also subtract scrap sale revenue. (Financial Architect's edge case analysis, confirmed by Implementation Realist as a real coupling.)

**Also fix:** `COST_RECOVERY` (4100) is typed as `REVENUE` but is actually a contra-expense. Devil's Advocate found this. **Add a `CONTRA_EXPENSE` account type** to the `AccountType` enum, or net `COST_RECOVERY` against COGS in the trial balance presentation. This is a classification fix, not a posting change — defer the actual reclassification to Phase 3 (it affects trial balance presentation only, not balances).

**Pre-existing bug to document (Edge Case Hunter EC-2.6):** `scrap.ts:147-150` has a race condition in `updateMany` for `refId`. The DPR auto-scrap path already fixed this by creating the record first. The manual path should be refactored similarly. **Document as known issue, fix alongside the GL wiring.**

### 1C. Payroll NET → GROSS Fix (3 days, not 2)

**The bug:** `postPayroll()` posts `totalNet` as expense. Should post `totalGross` with deductions as separate liabilities.

**Round 3 found 2 BLOCKERS and multiple hidden complexities:**

#### BLOCKER 6: ESI field doesn't exist on PayrollLine

**Problem:** `PayrollLine` has `pf`, `tax`, `deductions` — but NO `esi` field. The Round 2 design proposed `ESI_PAYABLE (2350)` but there's no data source for `totalESI`.

**Fix:** **Split the payroll fix into two sub-tasks:**

**1C-i (Phase 1): PF + TDS payable posting** — these fields exist on `PayrollLine`. Fix `totalGross` accumulator, post GROSS expense with PF and TDS as separate payables. ~2 days.

**1C-ii (Phase 3): ESI + profession tax** — these require schema migrations (`esi` field on `PayrollLine`, profession tax account), service changes, and UI changes. This is a full vertical feature, not a bug fix. ~1 day + schema migration.

#### BLOCKER 7: Employer PF contribution missing

**Problem:** `PayrollLine.pf` comment says "provident fund (employee + employer)" — it combines both. The design only handles employee PF (deduction). Employer PF (12% of basic, additional expense) is missing.

**Fix:** For Phase 1, assume `pf` field = employee deduction only (despite the comment). Compute employer PF separately as `basicAmount × 0.12` if needed. **Or:** split `pf` into `employeePf` and `employerPf` fields (schema migration). Given the scope, **defer the employer PF split to Phase 3** and document the assumption.

**Revised Phase 1 payroll posting (1C-i):**
```
Dr SALARIES_EXPENSE (6100)    [totalGross]           ← FIX: was totalNet
Cr SALARIES_PAYABLE (2200)    [totalNet]
Cr PF_PAYABLE (2250)          [totalPF]              ← NEW account
Cr TDS_PAYABLE (2400)         [totalTDS]             ← existing account
Cr OTHER_DEDUCTIONS           [totalDeductions - PF - TDS]  ← residual
```

**No ESI_PAYABLE in Phase 1** (field doesn't exist). No employer PF in Phase 1 (deferred).

#### Additional fixes required:

1. **Fix `generatePayroll()`** (`hr.ts:703`): change `totalGross.plus(basicAmount)` → `totalGross.plus(grossPay)`. Also fix `updatePayrollLine()` (`hr.ts:775`): change `acc.gross.plus(l.basicAmount)` → `acc.gross.plus(l.grossPay)`. Both must be fixed or manual adjustments will re-corrupt `totalGross`.

2. **Fix `totalDeductions`** (`hr.ts:705`): currently accumulates only `deductions`, not `deductions + pf + tax`. Must include all three.

3. **`processPayroll()` must sum line-level PF/TDS** since `PayrollPeriod` has no `totalPF`/`totalTDS` fields. Compute on-the-fly from `period.lines` (it already does `include: { lines }`).

4. **Verify "latent" claim:** Before starting, run a read-only query: `SELECT COUNT(*) FROM PayrollPeriod WHERE status IN ('PROCESSED','PAID') AND totalDeductions > 0`. If >0, there's existing bad GL data needing a correction entry. (Devil's Advocate's challenge.)

5. **Add `PF_PAYABLE` (2250)** to `CHART_OF_ACCOUNTS` and `ACCT`. Run `seedChartOfAccounts()`.

#### Schema Migration Required

No schema migration for Phase 1C-i (PF and TDS fields already exist). Phase 1C-ii (ESI) requires:
```prisma
// Phase 3 — add to PayrollLine
esi Decimal @default(0) @db.Decimal(14, 2)
```

### 2A. RERA Schema Fields — Carpet/Super-Built-Up Area (3 days)

> **Business Owner:** "RERA is not a nice-to-have. It's a legal requirement. Phase 3 is unacceptable."

**Moved from Phase 3 to Phase 2** per Business Owner's challenge. Non-compliance risk: penalties up to 5% of project cost under RERA Section 63.

**Schema migration:**
```prisma
// Add to BuiltUnit (all nullable — backward compatible)
carpetArea       Decimal? @db.Decimal(14, 3)  // RERA carpet area
superBuiltUpArea Decimal? @db.Decimal(14, 3)  // saleable area
balconyArea      Decimal? @db.Decimal(14, 3)
clearHeight      Decimal? @db.Decimal(14, 3)
hasLoadingDock   Boolean  @default(false)
```

**Frontend ripple effects (6 surfaces — Frontend Lead identified):**
1. Built unit form — add 2 inputs per row
2. Cost-per-sqft calculation — which area drives allocation? (product decision needed)
3. Pricing displays — which area for per-sqft pricing?
4. Portal listings — 99acres/MagicBricks require carpet area
5. Sales flow — RERA requires carpet area on sale documents
6. Reports — per-sqft metrics need to specify which area

**Semantic decision:** Default to `superBuiltUpArea` for pricing (current behavior — `area` field is used for sales). Use `carpetArea` for RERA disclosures. Migrate existing `area` → `superBuiltUpArea` (since that's what's currently used).
